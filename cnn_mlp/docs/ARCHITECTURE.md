# The TokaMark model (`MultiConv_MLP`), explained properly

A complete, plain-English **and** technically precise walkthrough of the network this
project trains on task_1-3. It follows the real code in
`tokamark_baseline/src/multi_conv_mlp_model.py` and `conv_encoders_decoders.py`
(commit `1e7c489`). Where useful it points at the readable reconstruction in
`docs/reference/architecture_multiconv_mlp_standalone.py`.

If you want the *questions-and-answers* style, that is `docs/VIVA.md` Part 6. This
file is the structured, deep reference.

---

## 0. The one-line summary, then the honest version

**One line:** take 8 magnetic-sensor signals over a 5 ms window and reconstruct the
2-D magnetic equilibrium field (`psi`) they came from.

**Honest, complete version:**

```
8 signals (different lengths)
   │
   ├─► Conv-encoder per signal  ──►  32-number fingerprint   (× 8, independent)
   │        "per-channel CNN"
   ▼
concatenate                                    256 numbers
   ▼
encoder MLP:  256 → 64 → 32                    "bottleneck / context"
   ▼
decoder MLP:   32 → 64 → 32                    "condition the latent"
   ▼
broadcast across W_out windows (W_out = 1)
   ▼
Conv-decoder  ──►  65 × 65 psi field
```

So the architecture is **per-channel CNN encoders → concat → MLP → MLP → broadcast →
CNN decoder**. It is *not* a single MLP: there are **two MLPs** (an encoder MLP and a
decoder MLP) wrapped around a **32-dimension bottleneck**, and a **broadcast** step
between the MLPs and the decoder CNN.

---

## 1. What the model is asked to do

A tokamak is a donut-shaped fusion reactor. Its plasma is held by an invisible
magnetic "bottle". We cannot see that bottle directly; we infer it from magnetic
sensors on the vessel wall, using the **Grad–Shafranov** physics relation. The
inferred quantity is `psi` — the poloidal flux function over the (R, Z) cross-section.

The target task (TokaMark `task_1-3`) is therefore:

> **Inputs:** 8 sensor signals over a **5 ms** window (`input_length = 0.005 s`).
> **Output:** the `psi` field on a **65 × 65** grid for the **same** window.

This is **regression** (we output real-valued field numbers), and it is **Markovian**
(`task_type: markovian`) — the answer depends only on the current instant, not on the
history before it. That last fact is *why* a feed-forward design is the fair baseline,
and why an MLP bottleneck (not a recurrent one) is appropriate. See §9.

---

## 2. What goes in — the 8 channels, precisely

The model is **not** a single tensor input. It receives a **list of 8 tensors**, one
per signal, and each has a different shape. From the runtime smoke test, as `(C, T)`:

| # | Signal | Shape `(C, T)` | Notes |
|---|--------|----------------|-------|
| 0 | `magnetics/flux_loop_flux` | `(1, 25)` | flux loop |
| 1 | `magnetics/b_field_pol_probe_ccbv_field` | `(1, 25)` | pickup coil |
| 2 | `magnetics/b_field_pol_probe_obr_field` | `(1, 25)` | pickup coil (outboard) |
| 3 | `magnetics/b_field_pol_probe_obv_field` | `(1, 25)` | pickup coil (outboard vert.) |
| 4 | `magnetics/b_field_tor_probe_saddle_voltage` | `(1, 250)` | **10× denser/longer** |
| 5 | `pf_active/coil_current` | `(1, 20)` | active coil current |
| 6 | `pf_active/solenoid_current` | `(1, 20)` | solenoid current |
| 7 | `summary/ip` | `(1, 20)` | total plasma current |

At the model boundary, after the dataset's transforms, each is shaped
`(B, W, C, L)` with a single window `W = 1`, channel `C = 1`, and samples `L = T`.
(`B` = batch size, 512 in our runs.) The batch is therefore a **list of 8 tensors**,
one of which is `(512, 1, 1, 250)` and the rest `(512, 1, 1, 25 or 20)`.

**Why this shape:** `C = 1` because these are *scalar* physical measurements (one
number per time sample), not multi-channel coloured images. `L` differs per signal
because MAST samples different diagnostics at different rates and TokaMark keeps the
native sampling within the 5 ms window.

**Key framing:** think "a stack of sensor traces", **not** a photograph. Some are
2-D blocks `(time, sensors)` in other tasks, but for task_1-3 they are 1-D traces.

### 2.1 Exogenous inputs (none here)
The code also supports **exogenous** inputs — *future* actuator commands the machine
already knows (e.g. planned coil waveforms). For task_1-3 the exogenous list is
**empty**, so that whole path is skipped. This matters because it simplifies the
decoder-MLP input to "context only" (§4, Stage D).

---

## 3. What comes out

A single field per window:

```
(B, 1, 65, 65)
```

For each of the `B` windows, one **65 × 65 grid** of `psi` values. In the decoder it
is generated by treating the **65×65 grid as a 1-D axis of length 65 with 65
channels** (§5 explains the trick). Because it is rendered with `imshow`, it *looks*
like an image, but it is a physical field.

---

## 4. The architecture, stage by stage (with the real operations)

The class is `MultiConv_MLP`. Six stages:

### Stage A — one CNN encoder per input channel ("the specialists")
There are **8 independent encoders**, one per signal. Each encoder is
`Conv1DEncoder(input_shape=(C, T), D=16, layers=3, k=3, s=3, p=1, bb=2)`.

Inside one encoder, the operation order is **repeated 3 times**:

```
BatchNorm1d(C)                    # normalise the raw signal first
for each of 3 layers:
    Conv1d(in→out, k=3, s=3, p=1)
    ReLU()
    MaxPool1d(2, padding=1)
    BatchNorm1d(out)
then:
    flatten  →  Linear(final_channels * ts_comp  →  D*bb = 32)
```

Channels per layer: **16 → 32 → 64** (they double each layer;
`final_channels = D·2^(layers−1) = 16·4 = 64`). The stride-3 conv plus a max-pool of 2
**aggressively shrink the time axis**. The function that computes the final length is
`compressed_size_encoder`, which applies, per layer:
```
L = (L + 2p − k) // s + 1          # Conv1d
L = (L + 2p − 2) // 2 + 1          # MaxPool1d(2, p=1)
```
For a 25-sample channel that gives **25 → 9 → 5 → 2 → 1** (see the worked trace, §31).
For the 250-sample channel it collapses to 1 as well, just from a bigger start.

**The point of Stage A:** whatever the signal's *length* and *physical unit*, it comes
out as a fixed **32-number vector**. Heterogeneous sensors → uniform fingerprints.
Each branch learns its own features, in isolation from the other 7.

### Stage B — concatenation ("the meeting")
The 8 fingerprints are concatenated along the feature axis:
```
(B, W=1, 8 × 32)  =  (B, 1, 256)
```
256 numbers = the model's entire instantaneous view of the plasma. For task_1-3,
`W_in = 1`, so this is a single vector per example.

### Stage C — encoder MLP ("the bottleneck / context")
```
Linear(256 → 64) → ReLU → Linear(64 → 32)
```
It mixes all 8 sensors into **one 32-number context vector** — the network's compressed
"state of the plasma right now". The general form is
`Linear(D·bb·n_in·W_in → 2·D·bb) → ReLU → Linear(2·D·bb → D·bb)`; with n_in=8 and
W_in=1 that is `256 → 64 → 32`.

### Stage D — decoder MLP ("condition the latent")
```
Linear(32 → 64) → ReLU → Linear(64 → 32)
```
Takes the context and produces the **latent the CNN decoder will consume**. With
exogenous inputs it would concatenate those fingerprints first
(`D·bb·(1 + n_exo·W_out)` input width); here there are none, so it is `32 → 64 → 32`.
Having two MLPs lets the model apply a nonlinear transform *before* and *after* the
narrow 32-dim bottleneck (i.e. the bottleneck is genuinely an information squeeze).

### Stage E — broadcast ("stamp the latent across windows")
The 32-vector is `unsqueeze(1).repeat(1, W_out, 1)`. For task_1-3, `W_out = 1`, so it
is `(B, 1, 32)` — trivially broadcast. (In a multi-step task, the *same* context
would be stamped at every output step, since the decoder has no recurrence of its own.)

### Stage F — one CNN decoder per output channel ("the painter")
A `Conv1DDecoder` — the mirror of the encoder — using **`ConvTranspose1d`**:

```
Linear(32 → final_channels · len_deepest)      # e.g. 64 · 3
view → (64, 3)
3 × [ ConvTranspose1d(k=3, s=3, p=1, output_padding=1)  ( + ReLU + BatchNorm except last) ]
   each cropped back to an exact target length
```

It first expands the latent to `(64, 3)`, then **upsamples** through the length ladder
that `list_compressed_size_decoder(65, 3)` returns: **`[3, 8, 22, 65]`** (deepest →
final). Each `ConvTranspose1d` enlarges the axis and the code **crops** it to the exact
ladder length, so the final size lands exactly on 65. Because the output branch for
`psi` is shaped as a length-65 axis with 65 output channels, the result is the
`(B, W_out, 65, 65)` field. There is **no final activation** (raw regression output).

## 5. The shape arithmetic (worked trace, D=16, bb=2, layers=3)

Take channel 0, `(C,T) = (1,25)`:

```
input (1, 25)
 BN(1)
 Conv1d(1→16, k3 s3 p1)   len 25 → 9
 ReLU, MaxPool(2,p1)      len 9  → 5
 BN(16)
 Conv1d(16→32, ...)       len 5  → 2
 ReLU, MaxPool(2,p1)      len 2  → 2
 BN(32)
 Conv1d(32→64, ...)       len 2  → 1
 ReLU, MaxPool(2,p1)      len 1  → 1
 BN(64)
 flatten → 64·1 = 64
 fc: 64 → 32                              ← channel fingerprint

8 channels → concat → 256
encoder_mlp: 256 → 64 → 32
decoder_mlp:  32 → 64 → 32
broadcast   → (B, 1, 32)

psi decoder: fc 32 → 64·3
 ladder 3 → 8 → 22 → 65  (ConvTranspose1d, cropped)
 output: (B, 1, 65, 65)
```

Parameter scale: the whole model is **~0.3 M parameters** (measured at init). Tiny by
modern standards — a useful fact, because at that size plus a small dataset the model
can **memorise** rather than generalise (see `docs/EXPLAINED.md` §4.5).

## 6. The building blocks, verbatim meaning

### 6.1 `Conv1DEncoder`
- **What it is:** stack of `[Conv→ReLU→MaxPool→BatchNorm] × 3`, then flatten + `Linear`.
- **Channels:** `C → D → 2D → 4D` (i.e. 1 → 16 → 32 → 64).
- **Time shrink:** governed by stride 3 + pool 2, see §5.
- **Output:** a `D·bb_factor`-length vector (32).
- **BatchNorm first:** normalises the raw input signal inside the block too (in
  addition to dataset-level standardisation).

### 6.2 `Conv1DDecoder`
- **What it is:** `Linear` up to `(final_channels, deepest_len)`, then
  `[ConvTranspose1d (+ReLU+BatchNorm, except last)] × 3`, cropping each step.
- **Output:** `(n_var, ts_var)` = the requested field shape (65, 65).
- **Why "transpose":** a transposed convolution is a convolution run "in reverse" —
  it *enlarges* a small axis instead of shrinking it, with `output_padding`/cropping to
  hit the exact target length.

### 6.3 Other dimensionalities exist
Upstream also has **Conv2D/3D** encoder/decoder variants (structurally identical, for
tasks whose inputs are `(C, T, H)` / `(C, T, H, W)` profiles or images). **task_1-3 uses
only the 1-D variants.**

## 7. Config knobs and what each controls

| Knob | Value | What it does | Effect if changed |
|---|---|---|---|
| `D` | 16 | base feature width; channels double per layer | ↑ = wider, more capacity/params |
| `bb_factor` | 2 | bottleneck multiplier; fingerprint size = `D·bb` | ↑ = wider bottleneck |
| `layers_encoder` | 3 | conv blocks per encoder | ↑ = deeper/stronger encoders |
| `layers_decoder` | 3 | transpose-conv blocks per decoder | ↑ = deeper decoder |
| `kernel_size` | 3 | conv window | ↑ = wider receptive field |
| `stride` | 3 | conv step | ↑ = more aggressive downsampling |
| `padding` | 1 | edge preservation | keeps shapes sane |
| pooling | `MaxPool1d(2, p=1)` | halves the axis after each block | drives the shrink |
| `output_padding` | 1 | decoder upsampling fix | ensures exact target length |

> **Trap:** the conv file's default `BB_FACTOR = 3`, but the **model file injects
> `bb_factor = 2`**, so the model wins and fingerprints are 32, not 48. If you ever see
> a mismatch in shapes, check this.

## 8. Parameter count / depth / speed (why it is cheap)

Path depth from input to output is small: BatchNorm + 3 conv blocks + Linear (encoder) →
2 MLPs (bottleneck) → Linear + 3 transpose-conv blocks (decoder). That modest depth is
why it **builds in a few seconds** and runs ~130–250 ms/step. Total ≈ **0.3 M params**.
The compute is dominated by the wide input (the 250-sample channel) and the 65×65 output
decoder.

---

## 9. Why this design fits task_1-3 (the rationale a viva will probe)

1. **Per-channel encoders** suit heterogeneous sensors of different lengths/units. You
   do not have to resample or pad them into one grid.
2. **A bottleneck** (32 dims) forces a compact state — regularising, and cheap.
3. **Markovian task ⇒ no recurrence needed.** The output depends only on the current
   instant, so a feed-forward MLP bottleneck is the correct, fair baseline. A recurrent
   (LSTM) or continuous-time (Liquid NN) bottleneck would have almost no temporal axis
   to act on here (`W_in = W_out = 1`), so little/no gain is expected — an interesting
   *negative* result rather than a defect. See `docs/VIVA.md` §Q6.5.
4. **The per-channel design has a cost:** because encoders cannot share information
   *across* channels early, losing an entire channel at inference hurts more than for a
   model that mixes channels sooner. This is directly relevant to the robustness study
   (Gupta found the CNN most sensitive to active-coil removal).

## 10. How the model is trained (surrounding setup)

- **Loss:** `MultiOutputMSELoss` — MSE against the true `psi`, averaged over outputs.
- **Optimiser:** Adam, `lr = 1e-4`, `weight_decay = 1e-4`.
- **Batch:** 512 windows.
- **Standardisation:** inputs and targets are z-scored using **train-split** statistics,
  then reported metrics are un-standardised back to real units. **Training loss is on
  the standardised scale; NRMSE is on the raw scale** — two rulers, same error
  (`docs/EXPLAINED.md` §4.2).
- **Early stopping:** validation loss checked every 100 steps; stop after 10 non-improving
  checks ("patience 10"); keep the best checkpoint. Both our runs stopped at step 3500.
- **Two GPUs:** `DataParallel` (`use_dp = auto`) splits the batch across both T4s for
  throughput only.

## 11. The two variants (MLP vs LSTM bottleneck)

Both variants share the **same CNN encoders and decoders**; only the **bottleneck
differs**:

| Variant | File | Bottleneck | Appropriate for |
|---|---|---|---|
| `MultiConv_MLP` (**we run this**) | `multi_conv_mlp_model.py` | plain MLP | **Markovian** tasks (task_1-3) |
| `LSTM_v3` | `multi_conv_lstm_model.py` | LSTM (carries state) | non-Markovian / forecasting |

Neither is "better"; the right one depends on whether the task needs memory. The MLP
file's docstring still says "LSTM" — a copy-paste fossil showing it was derived from the
LSTM variant.

## 12. Why this matters for robustness work

Because the inputs are **8 addressable sensor branches**, real-world failures map
cleanly onto them:

| Real-world failure | Simulation |
|---|---|
| a sensor dies | zero/mask one input channel (**channel ablation**) |
| interference | add noise / random dropout |
| a gap in data | blank a stretch of time (**temporal gap**) |
| corrupted readings | spikes, saturation, wrong gain |
| shared-cause failure | blank a physically-linked **group** at once |
| pre-disruption loss | blank the **end** of the window |

The `psi` output stays the same size, so we can measure exactly how much the
reconstruction degrades as we damage the inputs, apply **imputation** mitigations
(zero-/mean-/forward-fill), and compute the **Robustness Score**. Full plan in
`docs/ROADMAP.md` Stage 1 and `docs/VIVA.md` Part 7.

## 13. One-paragraph recap

`MultiConv_MLP` is a small **multi-branch convolutional encoder + 2-MLP bottleneck +
convolutional decoder**. Each of 8 magnetic-sensor signal channels gets its **own 1-D
CNN encoder** (`[Conv→ReLU→MaxPool→BatchNorm]×3` + Linear) that compresses it to a
**32-number fingerprint**; the fingerprints are concatenated to **256**, squeezed by an
**encoder MLP (256→64→32)** into a **32-dim context**, expanded by a **decoder MLP
(32→64→32)**, broadcast across output windows, and finally painted by a
**transposed-convolution decoder** into a single **65×65 `psi` field**. It is a
regression model of **~0.3 M parameters** taking time-windowed sensor readings in and
producing a 2-D magnetic-equilibrium field out — deliberately tiny, and (for a
Markovian task) deliberately feed-forward.
